# Architecture Decision Records (ADRs)

## ADR-001 – Stack e justificativa

**Status:** Proposed

**Decisão:** Utilizar a stack proposta (TypeScript, pnpm + Turborepo, React + Vite, PixiJS, Three.js, Fastify, ws, PostgreSQL + Drizzle ORM, Zod, Vitest, Playwright, Docker‑Compose).

**Motivo:**
- Linguagem única (TS) permite código compartilhado entre cliente e servidor.
- Turborepo simplifica gerenciamento de múltiplos pacotes.
- React + Vite garante hot‑module‑replacement rápido.
- PixiJS (2D) e react‑three‑fiber (3D) são bem estabelecidos e compatíveis com WebGL.
- Fastify é leve, com suporte nativo a plugins e WebSocket.
- ws fornece WebSocket puro e leve.
- PostgreSQL oferece consistência ACID; Drizzle ORM tem tipagem forte.
- Zod garante validação declarativa.
- Vitest + Playwright cobrem unit‑ e e2e‑tests.
- Docker‑Compose facilita ambiente reproducível.

**Alternativas descartadas:**
- **Node + Express** – mais pesado, menos performance que Fastify.
- **NestJS** – curva de aprendizado maior, overhead desnecessário para protótipo.
- **Socket.io** – abstração extra e protocolo não‑standard para WebSocket puro.
- **MongoDB** – ausência de transações fortes necessárias para persistência de estado.
- **Webpack** – Vite oferece experiência de desenvolvimento superior.

## ADR-002 – Modelo de sincronização (comandos + eventos autoritativos)

**Status:** Proposed

**Decisão:** O servidor será a única fonte de verdade. Clientes enviam **comandos** (ex.: `MoveToken`). O servidor valida, persiste, gera **eventos** que são broadcast a todos os clientes da mesma sala. O protocolo inclui versão (`v1`).

**Justificativa:** Simplicidade, controle autoritativo, compatibilidade com futuros CRDTs se necessário.

**Alternativas descartadas:**
- **Estado compartilhado (CRDT)** – complexo, desnecessário para fase 0.
- **Polling** – latência maior, carga excessiva.

## ADR-003 – Modelo entidade lógica vs. representações 2D/3D

**Status:** Proposed

**Decisão:** Definir `Entity` contendo identificador estável e dados lógicos (posição lógica, atributos). Separar `Representation2D` e `Representation3D` que mapeiam a `Entity` a objetos de renderização. O servidor só conhece `Entity`; o cliente decide qual representação usar.

**Benefício:** Permite trocar visualizações sem mudar lógica de jogo.

## ADR-004 – Estratégia de persistência

**Status:** Proposed

**Decisão:** Usar tabelas relacionais em PostgreSQL para entidades principais (`rooms`, `entities`, `rooms_entities`). Dados de ficha/atributos que podem ser extensíveis serão armazenados em colunas JSONB.

**Motivo:** Relacionamento forte entre salas e entidades; JSONB permite extensibilidade sem migrações frequentes.

## ADR-005 – Suposições da seção 27 (pendentes)

**Status:** Proposed

- **Web‑only** – UI será apenas web (React + Vite). Desktop pode ser considerado num futuro usando Tauri/Electron.
- **Hospedagem em serviço** – Deploy futuro em Vercel/Render/DigitalOcean; agora usamos Docker‑Compose local.
- **Cenas 2D e 3D separadas** – Cada sala pode carregar apenas um tipo de cena; mudança de tipo via comando `SwitchScene`.
- **Sistema de regras** – Definido apenas como “parser de fórmulas simples” (ex.: `2d6+3`).

## ADR-006 – Fluxo Git/GitHub e política de segredos

**Status:** Proposed

- Branch de trabalho: `fase-0/prototipo`.
- Commits pequenos e frequentes, estilo Conventional Commits.
- Push após cada commit.
- `.gitignore` cobre todas as vias de vazamento.
- Hook `pre‑commit` usa Husky + lint‑staged + gitleaks.
- CI GitHub Actions roda lint, type‑check, testes e varredura de segredos.
